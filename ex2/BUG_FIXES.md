# Exercise 2: the bugs we found and how we fixed them

This document explains two problems we found in our ex2 parser during a full review before submission: what went wrong, why, and what we changed. It is written so that someone who did not take part in the review can follow it from start to finish.

**Short version:**

| # | Problem | How serious | File changed | Change |
|---|---------|-------------|--------------|--------|
| 1 | A very large number (for example `99999999999999999999`) printed `ERROR(1)` instead of `ERROR` | **Real bug**: wrong output | `jflex/LEX_FILE.lex` | Check the number's length before converting it |

Both changes are small (two lines in the lexer, one word in Main), and every test passes after them. See the [How we tested](#5-how-we-tested) section.

## 1. Background: how our program reports results

The ex2 PDF (section 3) says the output file must contain exactly one of three things:

| Situation | Output |
|-----------|--------|
| The program is syntactically correct | `OK` |
| There is a **lexical** error (bad characters, bad number, bad string, bad comment) | `ERROR` |
| There is a **syntax** error (the tokens are fine, but in an illegal order) | `ERROR(line)`, where `line` is the line of the *first* error |

A lexical error prints **no line number**; a syntax error **does**. So our program must always know *which kind* of error happened. Getting the kind wrong means a wrong answer, even when we correctly noticed that there was an error.

### How the pieces talk to each other

Our program has three parts:

1. **The lexer** (`Lexer.java`, generated by JFlex from `jflex/LEX_FILE.lex`) reads characters and turns them into tokens like `INT(5)`, `ID(x)`, `PLUS`.
2. **The parser** (`Parser.java`, generated by CUP from `cup/CUP_FILE.cup`) asks the lexer for tokens one by one and checks that they follow the grammar.
3. **`Main.java`** starts the parser and writes the final answer to the output file.

When something goes wrong, the lexer or parser "throws" a problem object up to `Main`, and `Main` decides what to write. This is the key part of `Main.java`:

```java
try
{
    ...
    ast = (AstNode) p.parse().value;   // run the parser
    fileWriter.print("OK");             // if we got here, no errors
    ...
}
catch (Error e)
{
    /* Lexical error */
    fileWriter.print("ERROR");
}
catch (Exception e)
{
    /* Syntax error */
    ... fileWriter.print("ERROR(" + line + ")");
}
```

So **`Main` tells the two kinds of errors apart by the *type* of the problem object**:

- The lexer signals a lexical error with `throw new Error("LEXICAL_ERROR");`, so it lands in `catch (Error e)` and prints `ERROR`.
- The parser signals a syntax error with `throw new RuntimeException(String.valueOf(line));` (in `report_error` in the CUP file), so it lands in `catch (Exception e)` and prints `ERROR(line)`.

This design works well, **as long as every lexical problem really arrives as an `Error`**. Bug 1 is a case where it didn't.

## 2. Background: Java's two kinds of "something went wrong"

Both bugs come down to the same Java detail, so it is worth explaining once.

In Java, everything that can be thrown belongs to one family tree:

```
Throwable                      ← the parent of everything that can be thrown
├── Error                      ← "serious" problems
│   ├── (our) new Error("LEXICAL_ERROR")
│   └── StackOverflowError     ← ran out of memory for function calls   (Bug 2)
└── Exception                  ← "ordinary" problems
    └── RuntimeException
        ├── (our) new RuntimeException("<line>")   ← syntax error
        └── NumberFormatException                  ← text is not a valid number   (Bug 1)
```

A `catch` block only catches its own branch of the tree:

- `catch (Error e)` catches things under **Error** only.
- `catch (Exception e)` catches things under **Exception** only.
- `catch (Throwable t)` catches **everything**.

So:

- **Bug 1:** a `NumberFormatException` (under *Exception*) came out of the **lexer**. `Main` thought it was a syntax error.
- **Bug 2:** a `StackOverflowError` (under *Error*) hit a block that only had `catch (Exception ...)`, so nothing caught it and Java crashed.

## 3. Bug 1: huge integers gave the wrong error

### What the rules say

- The ex2 PDF, section 2: the grammar's terminals are the tokens defined in ex1. So ex2 uses ex1's token rules.
- The ex1 PDF, "Integers": an `INT` token is a non-negative integer between 0 and 2¹⁵−1 = **32767**, and "Integers out of this range are lexical errors."
- The ex2 PDF, section 3: for a lexical error the output is **`ERROR`**, with no line number.

So **any** number above 32767 is a lexical error, and the answer must be `ERROR`. It doesn't matter whether the number is `32768` or `99999999999999999999`.

### What our program did

| Input | Correct output | Our output (before the fix) |
|-------|----------------|-----------------------------|
| `int x := 32767;` | `OK` | `OK` ✅ |
| `int x := 32768;` | `ERROR` | `ERROR` ✅ |
| `int x := 99999999999;` | `ERROR` | `ERROR` ✅ |
| `int x := 99999999999999999999;` | `ERROR` | **`ERROR(1)`** ❌ |
| `int x := 123456789012345678901234567890` | `ERROR` | **`ERROR(1)`** ❌ |

Small numbers were fine; out-of-range numbers up to about 19 digits were fine. Only *really* huge numbers broke.

### Step by step: what happened

This was the lexer rule for integers (the same code as in ex1):

```
{INTEGER}           {
                        long val = Long.parseLong(yytext());
                        if (val > 32767) {
                            throw new Error("LEXICAL_ERROR");
                        }
                        return symbol(TokenNames.INT, Integer.valueOf(yytext()));
                    }
```

The idea: convert the digits to a number, and if it is bigger than 32767, throw our lexical `Error`. This is what happened on `int x := 99999999999999999999;`:

1. The lexer reads `99999999999999999999` (20 digits). It matches the `INTEGER` pattern, so this rule runs.
2. `Long.parseLong("99999999999999999999")` tries to convert the text into a Java `long`.
3. A `long` can hold at most **9,223,372,036,854,775,807** (19 digits). Our number is bigger, so `parseLong` **cannot** convert it and throws a `NumberFormatException`.
4. The program never reaches `if (val > 32767)`, so our own `throw new Error("LEXICAL_ERROR")` **never runs**.
5. The `NumberFormatException` flies out of the lexer, passes through the parser (CUP doesn't catch it), and arrives in `Main`.
6. `NumberFormatException` is under **Exception** (see the tree above), so `Main` treats it as a **syntax error** and goes into `catch (Exception e)`.
7. There, `Main` looks at the error message. For syntax errors the message is just a line number like `"7"`. Here the message is `For input string: "99999999999999999999"`, which is not a number, so `Main` uses its fallback and prints `ERROR(` + the lexer's current line + `)`.
8. Result: **`ERROR(1)`** instead of **`ERROR`**.

### "But we got 100 on ex1 with the same lexer!"

True, and in ex1 this code *was* correct. The lexer did not change; what changed is the code **around** it.

In ex1, `Main.java` had a single "catch-all":

```java
catch (Exception e) {
    ... errorWriter.print("ERROR");
}
```

In ex1 the only possible error output was `ERROR`, so it didn't matter what kind of exception arrived: everything became `ERROR`, which was the right answer.

In ex2, `Main` has to choose between `ERROR` and `ERROR(line)`, and it chooses by exception type. The same `NumberFormatException` that ex1 handled correctly by accident now goes down the wrong path.

### The fix

We changed two lines in `jflex/LEX_FILE.lex`:

```
{INTEGER}           {
                        String txt = yytext();
                        if (txt.length() > 5 || Integer.parseInt(txt) > 32767) {
                            throw new Error("LEXICAL_ERROR");
                        }
                        return symbol(TokenNames.INT, Integer.valueOf(yytext()));
                    }
```

### Why this works

- **Our `INTEGER` pattern never allows leading zeros** (`INTEGER = 0 | [1-9][0-9]*`, and a separate rule `0[0-9]+` already rejects things like `007`). So a number with more than 5 digits is at least `100000`, which is definitely more than 32767 and definitely a lexical error.
- **`||` stops early.** Java checks the left side first. If `txt.length() > 5` is true, it throws our `Error` right away and **never calls `Integer.parseInt`**, so the huge number is never converted and nothing can blow up.
- If the number has 5 digits or fewer, it is at most `99999`, which always fits in an `int`, so `Integer.parseInt` is always safe there. It then does the normal `> 32767` check.

So now **every** out-of-range number, however long, ends in our own `throw new Error("LEXICAL_ERROR")` and prints `ERROR`.

### Alternative we considered

We could instead have added this to `Main.java`, before `catch (Exception e)`:

```java
catch (NumberFormatException e) { fileWriter.print("ERROR"); }
```

That would also give the right output. We chose to fix the **lexer** because that is where the problem starts. The lexer should report *all* lexical errors the same way (as an `Error`), so that `Main`, and the next exercises' code, never has to know about this special case.

## 4. Bug 2: huge programs crashed after writing OK

### What happens after a successful parse

When parsing succeeds, `Main`:

1. writes `OK` to the output file and **closes the file**;
2. then, only for debugging, calls `ast.printMe()`, which prints the tree and writes the Graphviz picture file (`output/AST_IN_GRAPHVIZ_DOT_FORMAT.txt`).

Step 2 is wrapped in its own `try`, so that a problem while drawing the picture cannot spoil the answer:

```java
/* [5] Print AST and finalize Graphviz DOT file safely */
if (parseSucceeded && ast != null)
{
    try
    {
        ast.printMe();
        AstGraphviz.getInstance().finalizeFile();
    }
    catch (Exception ignored)
    {
        /* Do not affect parse output if Graphviz logging fails */
    }
}
```

### Why huge programs crash

Lists in our AST, like a list of statements or a list of declarations, are stored as a **chain**: each list node holds one item (`head`) and the rest of the list (`tail`). For example, `AstStmtList.printMe()`:

```java
public void printMe()
{
    ...
    if (head != null) head.printMe();
    if (tail != null) tail.printMe();   // ← calls printMe on the rest of the list
    ...
}
```

So printing a list of 10,000 statements means `printMe` calls `printMe`, which calls `printMe`... **10,000 calls deep**, one inside the other.

Every time a function calls another function, Java keeps a small note of where to come back to, on what is called **the stack**. The stack has a fixed size (usually around 0.5–1 MB). With thousands of nested calls the notes no longer fit, and Java throws a **`StackOverflowError`**.

On the computer we tested on:

| Statements in one list | Result before the fix |
|------------------------|-----------------------|
| 2,000 | fine |
| 5,000 | fine |
| 8,000 | fine |
| 10,000 | **crash** |
| 20,000 | **crash** |

The exact limit depends on the machine, but it is in the thousands.

### Why the existing `catch` didn't help

`StackOverflowError` is under **Error**, not **Exception** (see the tree in section 2). The block says `catch (Exception ignored)`, so it does **not** catch it. The error escapes `main`, Java prints a crash message and exits with **exit code 1**, which means "the program failed".

### Why that matters even though the file says OK

The output file already contains the correct `OK`; it was written and closed before `printMe()` ran. But the course's self-check script (and very likely the real grader) also checks the exit code: if Java's exit code isn't 0, it marks the test as failed without even reading the output file.

So a crash counts as a **failed test** even though the answer in the file is right.

### The fix

One word in `src/Main.java`:

```java
catch (Throwable ignored)
```

instead of `catch (Exception ignored)`. `Throwable` is the parent of both branches, so this now catches `StackOverflowError` as well. The program exits normally (exit code 0), and the `OK` in the file is untouched.

Important: only **this** `catch`, the one named `ignored` near the end of `Main.java`, was changed. The `catch (Exception e)` near the top, the one that prints `ERROR(line)`, must stay as it is. Otherwise lexical and syntax errors would get mixed up again.

### Can this change hurt us?

No:

- It runs only **after** the output file is written and closed, so it can't change the answer.
- The only thing it hides is a crash inside the *debugging* picture code, which isn't graded. The worst case is an incomplete `ast.jpeg` when running `make debug`.
- `Throwable` is basic Java and works on every Java version, including whatever runs on nova.

### How likely was this in real tests?

Low. The provided tests are 20 to 50 lines long, and you would need around 10,000 statements in a single list to hit the problem. But the fix costs one word, so there was no reason to keep the risk.

## 6. Everything else we checked (and found correct)

- **Grammar vs. the PDF (Table 2):** every rule matches, including the parts that are easy to get wrong:
  - a function body and a class body must have **at least one** statement/field;
  - `-` is allowed only directly before a number (`-5` is fine, `-x` and `-(1)` are errors);
  - `new ...` is allowed only on the right side of `:=` or in a variable declaration, not inside expressions, call arguments or `return`;
  - a call result cannot be used as a variable (`f().x` and `f() := 1` are errors).
- **Grammar conflicts:** CUP reports **0 conflicts**. We also checked that if the precedence lines are removed, there are exactly 81 conflicts, all of them the expected "which operator first" conflicts between the 9 binary operators (9 × 9). So the precedence lines solve exactly what they should and nothing else.
- **Operator precedence and associativity** follow Table 1 of the PDF (see the AST checks above).
- **Syntax error line numbers** are the line of the token where the error is discovered, the same convention as the expected outputs of the provided tests.
- **The lexer** follows every ex1 rule: identifiers, keywords, strings of letters only, integers without leading zeros and at most 32767, both comment types with only the allowed characters, and unclosed comments/strings as errors.
- **Lexical vs. syntax order:** whichever error comes first in the file wins. For example `int x := ;` followed by `@` on the next line gives `ERROR(1)`, and `int x := 5 $ ;` gives `ERROR`.
- **Output format:** exactly `OK`, `ERROR` or `ERROR(n)`, with no newline at the end, the same as the expected files.
- **Submission structure:** `ids.txt` has one ID per line; the zip has `ids.txt` and `ex2/` at the top; `Lexer.java`, `Parser.java` and `TokenNames.java` are **not** included (the PDF says CUP generates `TokenNames.java`, so we must not submit it); the `Makefile` has no hard-coded paths.

## 7. Things that look strange but are fine

- **`precedence nonassoc ASSIGN;` and the precedence lines for `[`, `(` and `.`** have no effect: removing them still gives 0 conflicts. They are harmless, so we left them.
- **`input/Input.txt`** is still the skeleton's sample (statements outside any function), so `make debug` shows a syntax error for it. It isn't graded.
- **A `// comment` on the last line with no newline after it** gives a syntax error. That is correct: the ex1 PDF says `//a` followed directly by end-of-file is *not* a comment, so its characters become normal tokens (`/`, `/`, `a`).
- **A missing `}` at the very end of the file** reports the line where the file ends. That is where the parser discovers the problem, and it matches how the skeleton reports errors (`lexer.getLine()`).
- **`Main.java` line 2:** `import java.io.PrintWriter;` was removed during the edits. That is harmless, because line 1, `import java.io.*;`, already imports everything in `java.io`, including `PrintWriter`.

## 8. Lessons for ex3 and later

1. **When code moves to a new exercise, re-check its assumptions.** The integer code was correct in ex1 only because ex1's `Main` turned every exception into `ERROR`. In ex2 the surrounding code became stricter, and a hidden case broke.
2. **Every lexical error should leave the lexer the same way** (as our `Error`), so later stages never have to guess.
3. **Know the difference between `Error` and `Exception`.** `catch (Exception e)` does not catch everything. Use `Throwable` only where you really mean "ignore anything", like the debug-only picture code.
4. **Test the extremes**, not only normal programs: the biggest allowed number and the first one too big, very long numbers, empty files, huge files, and errors on the first and last line.
5. **The AST will be used in ex3**, so it is good that we checked now that its shape follows the precedence rules. A wrong tree would cause wrong semantic checks later.
